# Security Audit Notes

Date: 2026-06-05

## Current Database Access Model

The app uses a public Supabase anon key in the browser and a custom session token stored in `localStorage`.
Admin and driver mutations are partly protected through `SECURITY DEFINER` RPC functions that accept `p_session_token`.

The main remaining risk is direct table access. A browser client with only the anon key can currently read operational tables directly, because many tables still grant access to `anon` and have permissive RLS policies.

## Verified With Anon Key

Read access was confirmed for these tables using the anon key and `select(..., { head: true, count: 'exact' })`:

- `clients`
- `routes`
- `entries`
- `logs`
- `driver_trips`
- `daily_costs`
- `cost_settings`
- `app_settings`
- `employees`
- `schedule_entries`
- `timeline_entries`
- `employee_months`

Direct read access was denied for:

- `users`
- `user_sessions`

RPC checks:

- `get_all_users` rejects an invalid session token.
- `reset_routes_id_sequence` is not callable by anon in the live project.
- `execute_sql` is not exposed in the live project.

## High Priority Findings

1. Direct table reads bypass app login

   Login currently controls the UI, but not all database reads. Anyone with the anon key can query many operational tables directly through Supabase REST.

2. Direct table writes still exist

   The frontend still writes directly to:

   - `logs`
   - `driver_trips`
   - `daily_costs`
   - `cost_settings`
   - `app_settings`

   These should move behind RPC functions that validate `p_session_token` and enforce role/ownership.

3. Session token is stored in `localStorage`

   This is practical for the current SPA, but any XSS would expose the custom session token. The app should avoid rendering unsanitized user-controlled HTML and should add a strict Content Security Policy before treating this as production-hardened.

4. First-password flow allows account claiming by username

   `set_first_password(username, password)` allows setting a password for any existing account that has no password. This works for the current onboarding flow, but it means an unclaimed account can be claimed by anyone who knows or guesses the username.

## Progress

- Added transitional RPC migration for `driver_trips` writes: `db/migrations/driver_trips_rpc.sql`.
- Updated the frontend so `driver_trips` writes go through session-token RPCs. Direct `select` reads remain for a later read-hardening phase.
- Added transitional RPC migration for `daily_costs`, `cost_settings`, and `app_settings` writes: `db/migrations/admin_costs_settings_rpc.sql`.
- Updated the frontend so writes to `daily_costs`, `cost_settings`, and `app_settings` go through admin session-token RPCs. Direct reads remain for a later read-hardening phase.
- Added transitional RPC migration for `logs` inserts: `db/migrations/logs_rpc.sql`.
- Updated the frontend logger so log inserts go through `insert_log(p_session_token, ...)`; the database now derives `user_name` from the session instead of trusting the browser.
- A source scan now shows no direct Supabase `insert`, `update`, `upsert`, or `delete` calls in `src`; only direct reads remain.
- Added delayed hardening migration `db/migrations/revoke_direct_table_writes.sql` to revoke direct `insert`, `update`, and `delete` on the formerly writable tables after the RPC frontend is deployed and tested.
- Added deployment order checklist: `SECURITY_DEPLOYMENT_CHECKLIST.md`.
- These migrations intentionally do not revoke table writes yet. Deploy and test the RPC path first, then run a separate revoke migration.

1. Move writes behind RPC

   Add session-token RPCs for the remaining direct writes:

   - `insert_log`
   - `save_driver_trip`
   - `delete_driver_trip`
   - `save_daily_costs`
   - `save_cost_settings`
   - `save_app_setting`

2. Move sensitive reads behind RPC

   Replace broad direct table reads with functions such as:

   - `get_app_data(p_session_token)`
   - `get_driver_day(p_session_token, p_date)`
   - `get_costs_month(p_session_token, p_month_key)`
   - `get_history(p_session_token, filters...)`

3. Revoke table access from anon/authenticated

   After the frontend uses RPCs, run a breaking hardening migration:

   ```sql
   revoke all on table
     public.clients,
     public.routes,
     public.entries,
     public.logs,
     public.driver_trips,
     public.daily_costs,
     public.cost_settings,
     public.app_settings,
     public.employees,
     public.schedule_entries,
     public.timeline_entries,
     public.employee_months
   from anon, authenticated;
   ```

4. Tighten password onboarding

   Replace public first-password setup with one-time invite/reset tokens generated by admin RPC.

5. Add browser-side hardening

   Add CSP headers in deployment, keep session tokens out of logs, and consider expiring sessions sooner than 30 days for admin accounts.
